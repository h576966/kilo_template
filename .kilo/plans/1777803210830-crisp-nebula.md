# Plan: Model Cost Controls & Reliability Rules

## Context

KiloTemplate currently assigns `deepseek-v4-pro` to the `plan` agent only — all other agents (code, ask, reviewer, flash-patch, flash-debug, ship, compaction, explore) use `deepseek-v4-flash`. The code agent and flash-patch agent already have a 2-failure escalation handoff pattern: after two failed fix attempts, they log the event via `scripts/log-event.mjs` and use the `question` tool to offer V4 Pro escalation as a human decision. The flash-debug agent has NO escalation mechanism at all.

Rules are loaded from `kilo.jsonc` `instructions` array. Non-scoped rules (`00-conventions.md`, `10-workflow.md`) apply globally. Path-scoped rules (`20-security.md`, `21-docs.md`, `22-backend.md`) use YAML frontmatter `paths:` to limit scope. New rules without `paths:` frontmatter will be global.

Key files:
- `kilo.jsonc` — config, agent model assignments, instructions array
- `AGENTS.md` — auto-loaded project instructions; contains agent table and workflow docs
- `.kilo/agents/*.md` — agent definition files (plan, code, ask, flash-patch, flash-debug, reviewer, ship)
- `.kilo/rules/*.md` — rule files loaded into agent context
- `scripts/log-event.mjs` — structured JSONL event logging
- `tests/validate.mjs` — template structure validation (currently ~123 checks)

## Approach

Create two new global rule files (non-scoped, no `paths:` frontmatter) that load into ALL agent contexts. These act as persistent instructions telling every agent how to manage model usage and context efficiently. Then update agent definitions to align with the new rules, fill the escalation gap in flash-debug, and sync AGENTS.md/README.md with the new philosophy.

This approach over alternatives:
- **Rules vs agent-body edits**: Putting model routing in global rules means ALL agents (including built-in compaction/explore) see them, not just the ones we override. Agent-body edits handle agent-specific changes (escalation handoff mechanics).
- **Separate files vs merging into 10-workflow.md**: Keeping model routing and context budget in their own files follows the "one concept per file" convention and makes them independently toggleable.
- **Non-scoped rules**: These policies apply to every task regardless of file type, so no `paths:` frontmatter.

## Implementation Steps

### Step 1: Create `.kilo/rules/11-model-routing.md` — Model Routing Policy

New global rule (no YAML frontmatter required — follows same format as `00-conventions.md`). Contains:

- **Default**: All normal implementation, debugging, review, documentation, and mechanical work uses V4 Flash.
- **V4 Pro triggers** (escalate deliberately, not automatically):
  - Same test fails twice after attempted fixes
  - More than 5 files require coordinated changes
  - Task requires changing public APIs, data models, or schemas
  - Task affects auth, authorization, billing, secrets, migrations, deployment, or irreversible operations
  - Worker cannot clearly explain the failure or root cause
  - Worker is uncertain about architecture, hidden coupling, or side effects
  - Context has become too large or noisy (exceeds effective reasoning window)
- **Anti-escalation** (do NOT use V4 Pro for):
  - Basic file search, reading logs, formatting
  - Simple docs edits, straightforward tests
  - Rewriting obvious boilerplate
  - Tasks where deterministic tools alone suffice
  - Single-line or single-file mechanical changes
- **Handoff protocol**: Escalation is always a human decision. Use the `question` tool to present the choice; never auto-switch models.

### Step 2: Create `.kilo/rules/12-context-budget.md` — Context Budget Policy

New global rule. Preferred context-loading flow:
1. Search first (grep, glob, codebase_search) — form a hypothesis before reading files
2. Read file outlines or relevant symbols — use `read` with limited offset/limit to scan structure
3. Read targeted snippets — narrow reads of the specific functions/blocks needed
4. Read full files only when multiple sections are needed simultaneously
5. Patch minimally — use `edit` for existing files, `write` only for new files
6. Run targeted tests — only the tests relevant to the change
7. Review diff — use `git diff` to verify scope is correct

Avoid:
- Reading many full files before forming a hypothesis
- Sending entire log files or stack traces into the model
- Keeping obsolete tool output in context after it has been acted on
- Continuing long loops (3+ iterations) without compaction or task restructuring
- Repeating the same full context when escalating to V4 Pro — only send the relevant failure evidence

## Handoff

After 2 failed attempts to fix the same issue — or if the task is out of scope — stop trying the same approach. Before showing the options, log the event: run `node scripts/log-event.mjs escalation_prompted flash-debug fail "<brief reason>"` via bash. Then use the `question` tool to ask:

## Risks / Edge Cases

- **Rule loading order**: The new rules are numbered 11-12, loading after 00-conventions and 10-workflow, before path-scoped rules 20-22. This is correct — cost/routing rules should follow coding conventions and workflow but precede file-specific rules.
- **validate.mjs `checkActivatedRules`**: This test only inspects rules with `paths:` frontmatter. Our new rules have no `paths:` and won't be counted. This is expected — non-scoped rules are validated by `checkRuleFilesExist` instead.
- **README directory tree**: Currently lists 5 specific rule files individually. Adding 2 more makes the tree verbose. Consider replacing the enumerated list with a summary line like `rules/ (coding standards, workflow, model routing, context budget, security, docs, backend)` — but that's a judgment call.
- **flash-debug steps limit**: flash-debug has `steps: 14`. Adding escalation logic with `question` tool usage might consume several steps. This should still fit within 14 steps for most cases.
- **Existing agent handoff text**: The code and flash-patch handoff sections already contain explicit V4 Pro escalation logic. Adding references to the global routing rule is additive and should not conflict.
- **Compaction/explore built-in agents**: These have no override files but will see the global rules since rules are loaded into all agent contexts. The context budget rule (Step 2) specifically helps compaction make better decisions about what to keep/drop.
- **No path-scoped frontmatter on new rules**: Confirmed by design — these rules apply to ALL work, not specific file types. The `activate-rules.mjs` script only processes rules WITH `paths:` frontmatter, so the new rules won't appear in `--list` output.
