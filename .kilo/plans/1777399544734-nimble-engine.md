# Plan: Evaluate Three Feature Suggestions for KiloTemplate

## Context

KiloTemplate is a minimal, local-first agentic development template with a structured Plan → Execute → Review workflow. Core characteristics:

- **Zero external infra** — Everything is file-based markdown, JSONC config, and a validation script. No frameworks, no Docker, no services beyond the LLM API.
- **Permission model** — Agent frontmatter already supports granular tool-level permissions (ask.md denies all write tools; reviewer.md has `edit: deny`, `bash: ask`). Granted via `kilo.jsonc` `permission.bash: allow`.
- **Verification gates** — `10-workflow.md` enforces Phase 2 (lint + tests pass) and Phase 3 (no CRITICAL issues). `validate.mjs` runs 81 deterministic structural checks.
- **Path-scoped rules** — Documented in AGENTS.md but never demonstrated. Rule files support YAML frontmatter with `paths: ["src/**/*.ts"]` to limit scope.

Three suggestions were received, described as "80/20 recommendation (lowest complexity, highest payoff)."

---

## Suggestion 1: Sandbox Profiles + Deterministic Pre-PR Checks

**What they want:** `.kilo/sandbox/strict.md`, `balanced.md`, `fast.md` with command allowlists, plus a branch naming/diff size/validation pre-commit hook.

### Assessment: REJECT

**Reason:** The permission system already handles tool-level access control, and per-agent it's more granular than profile-level profiles would be. The project is not an execution sandbox — it's a template for defining agent behavior. Adding policy profiles at a second abstraction level creates confusion about which layer takes precedence (global config, agent frontmatter, or sandbox profile?).

- The pre-commit hook (`validate.mjs`) already exists and can be run manually. Adding git hooks requires `.git/hooks/` manipulation or a setup script, which adds complexity for a template repo where hooks aren't shareable via git.
- Branch naming and diff size checks add ceremony without proportional value — a 4-file diff is not inherently safer than an 8-file diff.

**If anything, do this:** Add a one-line note in AGENTS.md that `validate.mjs` should be run before commits/PRs. That's it.

---

## Suggestion 2: Lightweight Eval Mode

**What they want:** `tests/evals/` with 5-10 fixed tasks (prompt → expected structural outcomes), `tests/eval-template.mjs` with pass/fail scoring, run in CI/nightly.

### Assessment: REJECT

**Reason:** This violates two core project tenets:

1. **"No external services beyond the LLM API"** — Behavioral agent evals require calling the LLM, which costs money and introduces non-determinism. Flaky tests are worse than no tests.
2. **The project validates structure, not behavior** — `validate.mjs` checks that configs are valid, agents are cross-referenced, commands link to real agents. These are deterministic and cheap. Agent behavioral evals ("does the plan agent produce a reasonable plan for prompt X?") are inherently subjective and fragile.

The SWE-bench approach (Dockerized test suites, 120GB disk) is the opposite of KiloTemplate's philosophy. The `agent-rules` approach (no eval harness at all, just rules) is the more aligned pattern.

**If anything, do this:** Nothing. `validate.mjs` already provides deterministic quality gates at the right abstraction level.

---

## Suggestion 3: Reusable Rules Packs → ADOPT

**What they want:** `.kilo/rules/packs/security.md`, `docs.md`, `backend.md` with an activation script.

### Assessment: ADOPT

**Reason:** This directly extends an existing, documented, but **never demonstrated** feature: path-scoped rules. The AGENTS.md already documents the frontmatter pattern:

```yaml
---
paths: ["src/api/**/*", "docs/*.md"]
---
```

But no rule file uses it. Creating 2-3 example packs:

- Makes path-scoped rules discoverable for template users
- Demonstrates the composable rules pattern from `agent-rules` (which this project already structurally supports)
- Adds zero infrastructure — everything stays file-based markdown
- Validates with the existing `validate.mjs` test suite (just needs a new check for packs directory validity)

### Implementation Plan

#### Step 1: Create rules packs directory and example packs

**Files to create:**
- `.kilo/rules/packs/security.md` — Path-scoped to `*.js`, `*.ts`, `*.py`, `*.env`. Covers: no hardcoded secrets, validate inputs, parameterized queries, least privilege.
- `.kilo/rules/packs/docs.md` — Path-scoped to `*.md`, `docs/**/*`. Covers: don't create docs without being asked, keep README in sync.
- `.kilo/rules/packs/backend.md` — Path-scoped to `src/api/**/*`, `src/db/**/*`. Covers: REST conventions, error handling, input validation at boundaries.

Each pack follows the existing rule file format (markdown with YAML frontmatter, `paths` field for scoping).

**model: Flash**

#### Step 2: Create activation script

**File to create:** `scripts/activate-rules.mjs`

Zero-dependency Node.js script (matching `validate.mjs` pattern):
- Copies selected pack files from `.kilo/rules/packs/` to `.kilo/rules/`
- Renames with numeric prefix (e.g., `security.md` → `20-security.md`) to maintain load order
- Skips if already present (idempotent)
- Reports what was activated/deactivated

Usage: `node scripts/activate-rules.mjs security docs` or `node scripts/activate-rules.mjs --deactivate security`

**model: Flash**

#### Step 3: Add packs directory to validation

**File to modify:** `tests/validate.mjs`

Add a `checkRulesPacks()` function:
- Verifies `.kilo/rules/packs/` directory exists
- Each pack file has valid YAML frontmatter with `paths` (required) and `description` (optional)
- No pack name conflicts with active rule filenames
- Warns (doesn't fail) if packs exist but none are activated

**model: Flash**

#### Step 4: Document rules packs

**Files to modify:** `AGENTS.md`, `README.md`

- AGENTS.md: Add a "Rule Packs" subsection under "Rules" explaining the convention
- README.md: Add `packs/` to directory tree, mention activation script in Workflow section, update agent count line if needed

**model: Flash**

#### Step 5: Run validation and verify

Run `node tests/validate.mjs` — all existing 81+ checks must pass, plus new packs checks.

**model: Flash**

### Risks / Edge Cases

- **Pack naming conflicts**: The activation script must prevent overwriting existing rule files (e.g., if user already has `20-security.md`). Use the `--force` flag to allow overwrites.
- **Load order**: Packs are activated with numeric prefixes (20-29) placed between conventions (00) and workflow (10) and any future project rules (30+). This is a convention, not enforced.
- **Path-scoped support**: Kilo must support path-scoped rule loading for this to work at runtime. The AGENTS.md already documents it as a convention; if the runtime doesn't support it, the packs still work as global rules (just less efficiently).
- **Validation compatibility**: The new `checkRulesPacks()` function must not break any of the 81 existing checks.

---

## Summary

| Suggestion | Verdict | Rationale |
|---|---|---|
| Sandbox profiles + pre-PR checks | **Reject** | Redundant with existing permission system; pre-commit hooks aren't shareable via git in template repos |
| Lightweight eval mode | **Reject** | Requires LLM API calls → non-deterministic tests, contradicts "no external services" philosophy |
| Reusable rules packs | **Adopt** | Extends existing underused feature (path-scoped rules), zero infrastructure, high educational value |

**Total effort:** 4 new files, 1 new script, 3 files modified. All changes are filesystem-only (no API calls, no Docker, no services).
