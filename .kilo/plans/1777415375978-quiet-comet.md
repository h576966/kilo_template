# Plan: Rename worker agent to code (override built-in code agent)

## Context

Kilo Code ships with 7 built-in agents including **code** (primary, full tool access, default chat agent). The project currently has a custom `worker` subagent for the Execute phase. The user wants to rename `worker` → `code` so the custom implementation agent overrides the built-in code agent, following the same two-layer override pattern used for `plan` and `ask` (kilo.jsonc model pin + `.kilo/agents/<name>.md` prompt override).

User chose **primary mode** for the code agent, replacing the built-in default chat agent.

## Approach

Rename `worker.md` → `code.md`, flip mode to `primary`, update identity line. Then propagate the rename across `kilo.jsonc`, `AGENTS.md`, `README.md`, `.kilo/rules/10-workflow.md`, `.kilo/agents/ask.md`, and `tests/validate.mjs`. Keep the prompt body unchanged — same verification gate, escalation policy, rules, and responsibilities.

## Risks / Edge Cases

- **Git rename**: Use `git mv` to preserve history. The old `worker.md` file must be deleted.
- **Primary mode implications**: Switching from subagent to primary means code becomes the default Kilo Code chat agent. The prompt body (verification gate, "execute steps as specified in the plan") is designed for Task-tool delegation — it should still work as a direct chat agent since it mirrors the general implementation role.
- **AGENTS.md table mode**: validate.mjs `checkAgentsMdTable()` has a hardcoded branch for primary (plan, ask) and subagent (reviewer, worker, ship). Must add code to primary branch and remove worker from subagent branch.
- **ask.md routing table**: The worker row in the alternative agents table must be updated to code so the routing advice stays accurate.
- **No breaking changes**: 7 agents remain (rename, not add). All existing checks must pass.
